# AI code review plan

Oddmash uses a maintainer-enabled central review service for public organization repositories and explicitly approved private organization repositories. Internal and personal repositories remain excluded. The service uses the smallest useful permission set.

## Phase 1: completed advisory pilot (historical)

- The initial pilot installed a GitHub App only on selected repositories. This was a pilot-only restriction, superseded by the maintainer-approved public organization rollout in Phase 3.
- Grant read access to repository metadata, pull requests, contents, and checks, plus write access to pull request review comments.
- Read the changed files, relevant root and nested `AGENTS.md` files, repository-specific review rules, the pull request description, and completed check results.
- Combine deterministic evidence from ESLint or the repository's equivalent linter, the implementation language's compiler or static checks, and test results with AI analysis. Reference existing failures instead of repeating their output.
- Prioritize actual bugs, security and privacy defects, performance regressions, and accessibility problems over style preferences. Review visual and interaction changes against the repository's design documents rather than a generic Oddmash aesthetic.
- Include file evidence, severity, confidence, and a concrete verification step for every finding. Avoid duplicate comments across reruns and overlapping tools.
- Do not approve or request changes in the report-only pilot. Never modify branches, expose secrets, publish artifacts, merge, or deploy.

Start with a low-risk public repository and run in report-only mode before posting comments. Compare findings with maintainer review, track false positives, redact sensitive content, and cap diff size and model spend.

## Phase 2: repository policies

- Let each repository define review focus and exclusions in `AGENTS.md` without copying product-specific rules into the organization baseline. Nested `AGENTS.md` files override broader guidance for their scope.
- Combine deterministic CI results with AI analysis. The bot should reference failing checks instead of rephrasing them.
- Deduplicate findings by repository, pull request, commit, file, line, and rule. Update or resolve its own stale comments when the code changes.
- Keep review logs minimal, define retention, and never store source or prompts longer than required to complete and audit the review.

## Phase 3: organization-wide review rollout

- The maintainer has enabled organization-wide installation and explicitly authorized automatic enrollment of current and future public Oddmash repositories, without requiring a separate review workflow in each repository. Validate the organization, installation, repository identity and permitted visibility at runtime; do not execute contributed code.
- Private repositories may use the central reviewer only under a separately approved repository identity allowlist and data-processing policy. New private repositories are not enrolled automatically. Internal and personal repositories remain excluded. Private auto-merge is available only after explicit maintainer approval under Phase 4; future private repositories remain manual until enrolled.
- Keep organization and personal installations separate so a repository transfer is not required for review coverage.
- Add a non-blocking status check only after the pilot demonstrates stable precision. For a maintainer-enabled independent App, approval applies to internal PRs with zero validated findings, no omitted files, and passing current checks. Publish high-confidence actionable findings for every author as a GitHub review comment with inline evidence, a neutral review check, and explicit maintainer disposition guidance. Reserve formal GitHub change requests for human reviewers. For a clean external PR, leave a review comment for `qtaghdi` to give final approval and merge. Incomplete evidence requires advisory publication and maintainer review. Do not automatically dismiss previous reviews or bypass branch protection. If an earlier Lead change request still blocks a corrected PR, `qtaghdi` checks the current diff and CI, records why the earlier findings are resolved, and uses GitHub’s authorized review dismissal before the final approval and manual merge. The maintainer may make a normal manual merge decision subject to existing required branch checks; neutral reviews never qualify for automatic merge. Wait for the final aggregate verify check before publishing a formal outcome; update same-head advisory reviews instead of posting duplicates. Avoid a clean interim review while CI is pending or failing. Automatic release and secret access remain out of scope. The advisory reviewer does not merge.
- Follow the organization default of opening PRs ready for review. Draft PRs are deliberately excluded from official review until ready; pending remote CI alone is not a reason to use a draft. This does not relax the exact-head evidence or approval requirements.

Success means fewer escaped defects without adding noisy review work. Track accepted findings, dismissed findings, duplicate rate, review latency, cost per pull request, and any permission or data-handling incident.


## Cross-product quality and review dialogue

- Review visual clarity, accessibility, copyright/licensing and defensive security/privacy against the relevant product contract and actual changed-code evidence. Distinguish an actionable defect from a preference or missing context.
- WCAG 2.2.2 does not categorically prohibit intentional repeating demonstrations with a working pause, stop or hide mechanism. Respect reduced motion; evaluate actual behavior. Action buttons may change their labels; toggles using aria-pressed should have a stable name. Do not demand mutually incompatible control patterns.
- Require concrete provenance, license terms or distribution evidence for a licensing defect. Uncertain provenance merits a question, not a claim of infringement. Never request exploit reproduction, credentials or private values.
- Bounded work and fail-closed behavior are deliberate. Do not require unlimited pagination or speculate about unsupported API response formats without evidence. A limitation with a clear operational diagnostic is not automatically a blocking defect.
- The maintainer may reply directly in an inline thread to discuss its evidence. Use `/review` alone on the first non-empty line of PR Conversation for a full Lead review, with optional context on later lines; inline `/review` requests scoped review of that thread. A bot mention is not required. Follow the [current agent command table](https://github.com/Oddmash/oddmash-agents/blob/main/docs/agent-family.md#slash-commands) for supported contexts. Let the first automatic review finish. Before any new request, inspect the current head, pending review checks, existing commands and submissions, and original threads. Collect and classify all available review findings before changing code. Group related verified fixes and regression tests into one coherent batch, run applicable local checks, inspect the entire diff, push the completed batch, and wait for current-head CI. Do not request a full review after individual fixes, commits, thread replies, label changes, or repeated CI polling. Reply once to each original thread with the final head and evidence. Exact-head verification and full re-review are separate decisions. Default to no new full review when the patch only implements existing reviewed findings, adds targeted regression tests, or changes non-substantive documentation, formatting, or metadata. For those cases, inspect the complete delta against the reviewed head, verify each finding, record the current head and passing applicable CI, and follow the manual merge rules. Request one full re-review only when the delta introduces substantive behavior outside the reviewed scope, materially changes security, permissions, data handling, public API or release behavior, leaves essential review coverage unresolved, or an explicit independent approval requirement cannot otherwise be satisfied. Record the concrete trigger before requesting; a changed SHA alone, optional advice, or a successful CI run is not a trigger. Never duplicate an in-flight request. Do not bypass required human approval, branch protection, exact-head automated merge approval, or other enforced gates. Never duplicate a pending request or repeat a completed formal review for an unchanged head. One authorized follow-up is permitted when previously missing evidence becomes available after an incomplete-evidence advisory at the same head and no automatic review is pending, or when a confirmed failed request needs an explicitly authorized retry. Optional advice alone does not justify a new full review. Never request reviews while another session holds an active implementation or review claim. Retry only the latest applicable required CI run. Replies are advisory and do not change approval state. Group new inline findings under a single submitted review, retaining distinct threads. Preserve authorization, exact-head checks, redaction, deduplication and protected-branch requirements.

## Following up on review findings

After pushing a fix and verifying it, reply directly in each affected inline thread. Include the change, the current head and what you actually verified. On repositories with automatic inline routing, an Oddmash bot finding accepts this format with the full 40-character current PR head.

```text
Fixed in <full-current-head-sha>: <what changed and how it was verified>
```

The thread identifies the owning bot. Where automatic routing is unavailable, prefix the reply with the authenticated account that opened the thread, such as `@oddmash-qa[bot]`. For human reviewers, use their account. For findings without an inline thread, write the evidence summary in PR Conversation and follow the bot's explicit reference and mention format.

The owning bot can check an authorized maintainer reply on an open, ready PR and resolve the thread when the current diff proves the correction and GitHub confirms resolution. Check the GitHub thread state after a confirmation. If the bot lacks permission, a repository maintainer can resolve it after verifying the evidence. For feedback not adopted, reply in the original thread with `Not adopted:` and explain why, with relevant evidence or constraints. Use `Deferred:` with the reason and a linked follow-up issue for work intentionally postponed. Do not use the `Fixed in` format for a change that was not made. A maintainer can resolve a justified non-adoption or deferral after an explicit authorized decision and a recorded outcome; otherwise keep disputed, deferred or unverified findings open. Verify the thread state after resolving. A resolved thread is not evidence of a code fix, CI success, approval or permission to merge.

Open the PR **Checks** tab and choose **Oddmash Reviewer / review** for the current stage where review progress is enabled. Lead reports active coordinated specialists in the same check. Approval is the formal review outcome shown on the PR and depends on the current head, CI and review coverage.

## Phase 4: maintainer-only auto-merge

The account policy applies to new work immediately. Older Lead deployments may still recognize the alternate account. Until the [runtime transition](https://github.com/Oddmash/oddmash-agents/issues/331) is deployed and verified, keep that account out of production queues and handle existing fork PRs through maintainer review and normal manual merges.

- The same GitHub App uses a separate deterministic merge policy. All current Oddmash product projects are eligible: the existing approved public product repositories (Juliya, Oddmash UI, Interaction Inspector, Boundra and Oddmash Mobile) and explicitly enrolled private repository identities. Juliya is the renamed Kowrap repository, not a new enrollment. Vertactics is private and is subject to the existing private enrollment policy; this documentation does not grant or change eligibility. Eligibility requires a same-repository PR authored by the verified maintainer `qtaghdi`, verified by both numeric ID and login, targeting a protected branch allowed for its repository class: product repositories may target `develop` or default `main`; `Oddmash/.github`, `Oddmash/oddmash-agents` and `Oddmash/oddmash-skills` remain main-only, subject to their separate exact repository and path allowlists. New unapproved repositories, external contributors, and security-sensitive organization policy changes remain manual. Private review filtering remains mandatory; confidential filenames, issue text, omitted patches and incomplete evidence block automatic merging.
- Require a single independently validated same-repository reference to an open issue with explicit acceptance criteria authored by the verified owner (`qtaghdi`, GitHub user ID `135234546`), zero review findings, exact-head App approval and all current checks passing. A standalone closing reference requires evidence for the full issue scope. A standalone `Refs #N` permits a coherent partial PR scope verified against the linked issue and current diff, using its acceptance checklist or Summary; it never closes the issue. Markdown issue-form headings and ordinary measurable bullets or checkboxes are accepted. Multi-issue release PRs and cross-repository references are valid contribution metadata but require manual merge; report that distinction rather than a missing-link error. Missing or ambiguous evidence leaves the PR open.
- The exact public `Oddmash/.github` repository (ID `1455305553`) is eligible for authorized internal same-repository PRs targeting protected `main` that change ordinary organization Markdown guidance: root `AGENTS.md`, `CONTRIBUTING.md`, `PULL_REQUEST_TEMPLATE.md`, existing English issue templates, the profile README and localized README and contributor guides. Workflows, configuration, CODEOWNERS, security, AI review policy, and other governance documents such as `docs/github-account-policy.md` remain manual. All other non-allowlisted paths remain manual. All existing issue evidence, current CI, exact-head approval, branch protection and normal merge gates apply unchanged.
- Eligible changes include ordinary Markdown documentation, allowlisted product source paths, and additive tests that do not remove assertions or disable tests. Architecture, configuration, generated code, permissions, releases, sensitive paths, test rewrites and policy changes require manual review.
- Eligible source/test roots are explicit: Juliya `src/`, `site/app/`, `site/components/`, `site/lib/` and additive `test/` or `site/test/`; Oddmash UI and Interaction Inspector `src/`, `demo/` and additive `tests/`; Vertactics `apps/editor/src/`, `apps/landing/app/` and additive `apps/editor/tests/`. Only added or modified JavaScript, TypeScript, CSS, and SCSS source files are eligible. For enrolled private repositories, use explicit product-specific source roots maintained in the private runtime; repositories with no approved source roots may merge only ordinary documentation. Agent and skill governance, runtime and instructions remain manual. Nested test files follow the additive-only rule; all excluded paths and the bounded review budget still apply.
- Public `Oddmash/oddmash-mobile` (repository ID `1473122877`) permits ordinary documentation, supported source under `src/` and `demo/`, and additive tests under `tests/` subject to the existing exclusions and gates. The first live verification uses a separate same-repository documentation PR targeting protected `develop` and records the current-head review, trusted `verify` check, and merge actor.
- Boundra additionally permits `packages/runtime/src/` and `packages/ui/src/` ordinary supported source files and additive tests under `packages/runtime/tests/` and `packages/ui/tests/`. Rust core changes remain manual.
- Enforce the trusted GitHub Actions verify check on the eligible target branch and every required repository-specific CI check, require an up-to-date branch, never bypass branch protection, and scope the short-lived write token to the eligible repository only. Use the verified head SHA for a normal merge commit. Do not squash or rebase. Keep a deployment kill switch; failure leaves the PR open.
