# Oddmash へのコントリビューション

[English](../../CONTRIBUTING.md) · [한국어](../ko/CONTRIBUTING.md) · **日本語** · [简体中文](../zh-CN/CONTRIBUTING.md)

公開リポジトリの Issue、PR のタイトルと本文、公開レビュー、貢献テンプレート、コミットメッセージ、変更履歴は英語で記載してください。製品ドキュメントの既存の多言語方針は維持し、必要に応じて翻訳を支援します。

Oddmash プロジェクトの改善にご協力いただきありがとうございます。

Oddmash は一人で運営する独立系ソフトウェアスタジオです。公開リポジトリでは範囲の明確な自発的コントリビューションを歓迎しますが、常時の採用や長期的なコミュニティ参加を前提としていません。受け入れ可否は、メンテナーの優先順位と各プロジェクトが公開している範囲に基づきます。

## 不具合を報告する

該当するプロジェクトで Issue を作成し、期待した動作、実際の動作、再現手順を記載してください。プロジェクトのバージョンと関連する環境情報も添えてください。公開またはローカルのテストページとダミーデータを使い、ログやスクリーンショットから認証情報、非公開ページの内容、個人データを除いてください。

## 変更を提案する

新機能やプロジェクトの複数箇所に及ぶ変更は、まず Issue を作成してください。小さな実装変更でも、範囲を明確にした Issue を作成し、PR 本文にリンクしてください。

## プロジェクト README の基準

- README はプロダクトの紹介ページとして書いてください。冒頭で何ができるか、誰に役立つか、どのような場面で使うかを具体例とともに示してください。
- スクリーンショット、短い動画、ゲームプレイのキャプチャ、またはデモで実際の使い方を示してください。画像には内容が分かる代替テキストを付け、イメージ図にはその旨を明記し、サンプルデータを使ってください。
- リポジトリのセットアップ、インストール、ローカル実行コマンド、実装メモ、ビルド、テスト、リリース、コントリビューション手順は README に含めないでください。
- 開発と検証に関するすべての手順は、プロジェクトの `CONTRIBUTING.md` に記載してください。必要に応じて README の末尾から短くリンクします。
- 英語、韓国語、日本語、簡体字中国語の内容、言語切り替えリンク、画像をそろえて更新してください。

共通 Node CI の利用方法は[英語版のガイド](../../CONTRIBUTING.md#shared-node-checks)を参照してください。

JavaScript/TypeScript リポジトリ内部では、`package.json` に固定した共通 pnpm バージョンと `pnpm-lock.yaml` を使用します。CI では `pnpm install --frozen-lockfile` でインストールします。npm レジストリへの公開と外部利用者向け npm、Yarn、Bun のインストール手順は維持します。

## 共通の開発基準

- リポジトリ固有の作業ルールはルートの `AGENTS.md` に置きます。[組織共通の基準](../../AGENTS.md)から始め、プロダクト、プライバシー、リリース、エンジン、UI、デザインに実際に必要な規則だけを追加します。
- CI の権限は最小限にし、再利用ワークフローはレビュー済みのコミットに固定します。ランタイムの組み合わせ、ブラウザーやエンジンの設定、デプロイ、リリース検証は各プロダクトのリポジトリで管理します。
- プロダクト固有の UI とビジュアル規則はそのプロジェクトに置きます。複数のプロダクトで同じ安定した動作が必要になった場合だけ、トークンやコンポーネントを共有パッケージに昇格させます。
- 認証情報、署名情報、ユーザーデータ、本番専用の値を、例、フィクスチャ、ログ、スクリーンショット、プロンプト、レビューコメントに含めないでください。
- 専門エージェントは助言を提供し、Lead は[組織レビューポリシー](../AI-CODE-REVIEW.md)に従って正式なレビューを提出できます。別途認可されたマージ権限はレビュー権限と区別します。初回レビューは自動実行とし、認可された手動の全体レビューでは PR Conversation コメントの最初の空行でない行に `/review` のみを記載し、補足は後続行に記載します。[コマンド表](https://github.com/Oddmash/oddmash-agents/blob/main/docs/agent-family.md#slash-commands)を参照してください。
- 元のレビュースレッドに、検証済みの修正は `Fixed in <full-current-head-sha>: <change and verification>`、不採用は `Not adopted: <reason and evidence>`、延期は `Deferred: <reason and linked issue>` として返信してください。実施していない修正を報告しないでください。検証または権限を持つメンテナーの明示的な判断後に解決し、未解決の指摘は開いたままにします。実際のスレッド状態を確認してください。解決は CI 成功や承認に代わるものではありません。[レビューへの対応](../AI-CODE-REVIEW.md#following-up-on-review-findings)を参照してください。

## プルリクエストを提出する

- リモート CI やレビューが進行中でも、原則として Ready for review の PR を作成してください。明示的な依頼、実装が実質的に未完成の場合、またはレビューを誤解させる重要な検証根拠の不足がある場合に限り Draft を使用し、その理由を記録して解消後すぐにレビュー可能な状態に戻してください。
- 変更範囲を絞り、関連する Issue を必ずリンクしてください。統合ブランチや部分的な作業には `Refs #123`、完了したデフォルトブランチへのマージにのみ `Closes #123` を使用します。
- プロジェクトの `CONTRIBUTING.md` に従って環境を準備し、チェックを実行してください。結果はプルリクエストに記載してください。
- 権限、収集データ、公開 API、デプロイ、リリース動作の変更点を説明してください。

## プルリクエストをマージする

Oddmash の公開リポジトリでは、プルリクエストのマージに GitHub の **Create a merge commit** のみを使用できます。スカッシュマージとリベースマージはリポジトリ設定で無効になっています。この方針は手動マージと自動マージの両方に適用されます。

## 貢献形式の検証

- [共通 PR テンプレート](../../PULL_REQUEST_TEMPLATE.md)の必須項目をすべて記入し、タイトルとメンテナーのトピックブランチのコミット件名に `fix: clarify focus` のような種類の接頭辞を付けます。外部コントリビューターや既存のリリースマージ履歴は書き換えません。
- 公開リポジトリの Web Issue フォームには必須項目があります。非公開のリポジトリ、API/CLI による作成、編集、メンテナーによる空の Issue ではフォームを迂回できるため、エージェントは内容とラベルを自ら確認します。
- [共通 CI 検証](../../CONTRIBUTING.md#contribution-format-checks)は読み取り専用で PR タイトル、本文構造、ローカル Issue の参照などを確認します。根拠と使用言語は別途レビューが必要です。各リポジトリはレビュー済み CI バージョンへの更新と PR 編集イベントの有効化が必要で、既存の必須チェックと権限を保持します。
- 方針を導入する Issue が作成された 2026-11-24 08:31:35 UTC 以降のローカル Issue には、対応する種類ラベル一つと必須フォーム項目が必要です。それ以前の Issue には遡及適用しません。
- [英語版のテスト専用 PR の例](../../CONTRIBUTING.md#example-a-small-test-only-pr-targeting-develop)の5つの見出しをそのまま使用してください。`scope / scope` の `Validate contribution metadata` の失敗はテストの失敗とは別です。ログを確認して PR 本文を修正すると、対応するリポジトリで CI が再実行されます。外部フォークではメンテナーの承認が必要な場合があります。
